2. Project Milestones and Deliverables
This section defines the major project milestones, their expected deliverables, acceptance criteria, and completion dates. The schedule follows the deadlines established by the course instructor and covers the project lifecycle from topic selection to final project submission and defense. The project is developed by a team of four students. As of 15 October 2026, the project topic has been approved, the Project Proposal Report (R1) and Software Requirements Specification (R2) have been completed, and the system architecture, API contracts, and data model have been designed. Backend development has started, while formal software testing has not yet been performed. The remaining schedule focuses on completing the Project Management Report (R3), preparing the Test Plan and conducting testing where implemented functionality is available (R4), integrating the implemented components, and preparing the final project documentation and demonstration. The target scope is the MVP specified in the SRS. However, the actual implementation scope depends on the time available and the progress achieved by the team. Any functionality not implemented or not verified by the final deadline will be explicitly documented as a limitation rather than reported as completed.

2.2.2 Detailed Milestone Deliverables

The deliverables are the approved SRS, the system architecture, API contracts, and the data model. The deliverable is the Project Management Report due on 15 October 2026. It formalizes the project schedule, deliverables, task ownership, milestone dates, dependencies, and risks. Screenshots or exported views must demonstrate real task organization or progress tracking.

Milestone M6: Test Plan and Testing (R4)
The primary deliverable is the Test Plan due on 21 October 2026. It defines how the implemented system will be tested and how test outcomes will be evaluated. Testing activities will be performed against the available implementation. Priority will be given to the central user workflows, backend API behavior, component integration, authorization and validation rules, and handling of errors. The exact test coverage depends on which features are operational by the testing deadline. The milestone is considered complete when the Test Plan contains the required sections and the available testing activities have documented results. Requirements that cannot be tested because the corresponding features are incomplete will be identified as not tested, with the reason recorded.

The deliverables are an integrated, demonstrable build, a draft of the final documentation, a presentation draft, and a defined demonstration scenario. The final deliverables include the final project report, presentation, software demonstration, test results, documentation, and repository reference. The final report should summarize the implemented functionality, compare actual results with the original objectives, explain the testing outcomes, and describe remaining limitations and future improvements. The milestone is considered complete when the final materials have been submitted and the project has been presented and demonstrated according to the defense requirements.

3. RACI Matrix
This section defines the roles and responsibilities of the project team using the RACI methodology. The purpose of the matrix is to establish clear ownership of project activities, avoid duplication of effort, and ensure that every task has an assigned person responsible for its execution and a person accountable for its completion.
The team consists of four members with distinct technical responsibilities. Timergalin Timur coordinates the overall project and develops the order-processing backend. Madenov Denis is responsible for frontend development, Tolmatskaya Irina owns the B2B backend, and Lavitskaya Alexandra owns the B2C backend.
The RACI matrix covers project coordination, implementation, integration, testing, documentation, and final delivery. The assignment of responsibilities follows the system scope defined in the Software Requirements Specification (SRS) and the milestones presented in Section 2.
For cross-functional activities, the project lead coordinates dependencies and deliverable completion, while each subsystem owner remains responsible for the technical quality and status of their own workstream. The matrix defines the primary distribution of responsibility; individual development tasks may be further decomposed into smaller assignments in the project management tool.

The exact implementation scope may be adjusted according to the remaining development time. Such adjustments do not change the assigned subsystem ownership. Each member remains responsible for reporting the actual status of their work, identifying blockers, and providing evidence of completed functionality and testing.
3.1.2 Responsibility Boundaries
To reduce ambiguity during implementation and integration, the following responsibility boundaries are established.
Project coordination. Timergalin Timur coordinates the overall schedule, monitors milestone progress, maintains visibility of cross-component dependencies, and raises issues that may affect the project deadlines. Each team member is responsible for keeping their assigned tasks and statuses up to date.
Frontend. Madenov Denis owns the client-side implementation and its integration with backend APIs. Backend business rules and persistent data management remain the responsibility of the relevant backend subsystem owners.
B2B backend. Tolmatskaya Irina owns seller-facing backend functionality. This includes seller operations and their associated authorization, validation, and interaction with other platform services.
B2C backend. Lavitskaya Alexandra owns buyer-facing backend functionality. This includes preparing page responses and coordinating calls to relevant upstream services for buyer-facing workflows.
Order-processing backend. Timergalin Timur owns the order-processing component. The B2C subsystem may initiate buyer-facing order operations, but the order-processing component remains responsible for the order-related logic assigned to it. The frontend communicates through the documented API contracts instead of directly accessing backend services.
Testing and integration. Each subsystem owner is responsible for verifying their own component and supporting integration testing. Timergalin Timur coordinates cross-component verification and the consolidation of test results. A task is not considered verified merely because its implementation has been committed; the relevant test or verification evidence must be recorded.
Documentation and final delivery. Each member provides accurate information about their own component. Timergalin Timur coordinates the completion of shared deliverables, while all members contribute to the final report, presentation, and demonstration. Every team member must participate in the final presentation, as required by the instructor.

3.2.2 Interpretation of the Main Assignments
The matrix follows several important principles.
Project coordination and reporting. Timergalin Timur is accountable for maintaining overall project visibility and coordinating shared deliverables. Other members are responsible for providing accurate status information for their own workstreams and contributing the technical information required for project reports.
Component implementation. Each technical workstream has one clear owner. Denis Madenov is accountable for frontend implementation, Irina Tolmatskaya for B2B backend development, Alexandra Lavitskaya for B2C backend development, and Timur Timergalin for the order-processing backend. This ensures that implementation issues have a clear owner and can be escalated when they affect integration or deadlines.
Cross-component integration. Integration requires contributions from all four members because the selected workflows depend on interactions between the frontend and backend components. Timurgalin Timur is accountable for coordinating this work, but each subsystem owner remains responsible for making their component available and resolving defects within their area.
Testing. Every developer is responsible for preparing and executing relevant tests for their own component. Cross-component testing requires cooperation between workstream owners and is coordinated by the project lead. The test results must reflect the actual execution status; functionality that has not been tested must not be reported as having passed.
Final delivery. Timergalin Timur coordinates the consolidated submission and defense preparation. Each member remains responsible for explaining and demonstrating their part of the system. The project lead's accountability for the shared result does not replace the responsibility of individual owners for their components.
