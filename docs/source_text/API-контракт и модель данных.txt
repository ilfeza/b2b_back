1.6. Денормализация
Важно: во всех ответах, где есть Product или Post, бэк вкладывает полный объект seller. Это защищает от N+1 запросов на фронте.
json
{
  "id": "p1",
  "title": "Чашка",
  "sellerId": "s1",
  "seller": { "id": "s1", "username": "keramika_ann", "displayName": "Анна Керамика", ... }
}

Часть 2. Модели данных
2.1. User
ts
interface User {
  id: string;
  username: string;          // уникальный, нельзя менять
  displayName: string;
  avatar: string;            // URL
  email: string;             // уникальный
  roles: ("buyer" | "seller")[];
  bio?: string;
  createdAt: string;
}
2.2. Seller
ts
interface Seller {
  id: string;
  username: string;
  displayName: string;
  avatar: string;
  bio?: string;
  followersCount: number;
  isFollowing: boolean;      // вычисляется для текущего юзера
  rating: number;            // 0–5, дробное
  productsCount: number;
  postsCount: number;
  joinedAt: string;
}
2.3. Product
ts
interface Product {
  id: string;
  title: string;
  description?: string;
  image: string;
  price: number;             // целое, рубли
  currency: "RUB";
  sellerId: string;
  seller: Seller;            // денормализация
  saleMode: "online" | "out_of_stock" | "deal_only";
  availableDeliveries: ("pickup" | "cdek")[];
  pickupPoints?: { city: string; address: string }[];
  dealContacts?: string;
  inStock: number;
  createdAt: string;
}
2.4. Post
ts
interface Post {
  id: string;
  sellerId: string;
  seller: Seller;
  title: string;
  body: html;
  coverImage?: string;
  products: Product[];       // прикреплённые товары
  createdAt: string;
  likesCount: number;
  commentsCount: number;
  isLiked: boolean;          // вычисляется для текущего юзера
}
Примечание:
Изменение API-контракта — посты теперь в HTML.
Поле Post.body теперь содержит HTML-строку (например, <h2>Заголовок</h2><p>Текст с <strong>жирным</strong></p><ul><li>пункт</li></ul>).
Обязательное требование: бэкенд должен санитизировать HTML перед сохранением в БД. Используйте:
Kotlin: библиотека OWASP Java HTML Sanitizer или jsoup в режиме Safelist.basic().
Альтернатива: сохранять как есть, но санитизировать на рендере (фронт уже это делает через DOMPurify, но это defense in depth — лучше санитизировать на обоих концах).
Зачем: клиент может отправить в body любой HTML напрямую через curl, минуя наш UI. Без санитизации на бэке злоумышленник запишет в БД <script>...</script>, и при рендере он сработает у всех читателей.
Что разрешаем: p, h1-h3, strong, em, s, ul, ol, li, blockquote, br.Что запрещаем: script, iframe, style, on* атрибуты, href="javascript:..."
2.5. Order
ts
interface Order {
  id: string;
  createdAt: string;
  status: "created" | "paid" | "shipped" | "delivered" | "cancelled";
  buyer: User;
  seller: Seller;
  items: { product: Product; quantity: number }[];
  delivery: "pickup" | "cdek";
  pickupPoint?: { city: string; address: string };
  trackingNumber?: string;
  total: number;
}

Часть 3. Auth
3.1. POST /auth/login
Вход по email и паролю.
Body:
json
{ "email": "user@example.com", "password": "secret123" }
Response (200):
text
Set-Cookie: auth-token=<jwt>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=3600
json
{
  "data": {
    "user": {
      "id": "u1",
      "username": "ivan",
      "displayName": "Иван Петров",
      "avatar": "https://...",
      "email": "user@example.com",
      "roles": ["buyer"],
      "createdAt": "2025-01-01T10:00:00Z"
    }
  },
  "error": null
}
Ошибки:
401 UNAUTHORIZED — неверный email/пароль.
400 VALIDATION_ERROR — пустые поля.
3.2. POST /auth/yandex
Обмен code от Яндекс ID на сессию.
Body:
json
{ "code": "abc123", "state": "xyz789" }
Response (200):
text
Set-Cookie: auth-token=<jwt>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=3600
json
{
  "data": { "user": { ... } },
  "error": null
}
Логика бэка:
Обменять code на токен Яндекса (server-to-server с client_secret).
Получить профиль (email, name, avatar).
Найти или создать User в БД.
Если новый — роль buyer.
Выпустить свою сессию (cookie).
3.3. POST /auth/register
Регистрация через email/пароль. Всегда создаёт buyer.
Body:
json
{
  "email": "new@example.com",
  "password": "secret123",
  "displayName": "Иван",
  "username": "ivan_petrov"
}
Response (201): та же cookie + { user }.
Ошибки:
409 CONFLICT — email или username уже занят.
3.4. POST /auth/logout
Response (200):
text
Set-Cookie: auth-token=; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=0
json
{ "data": null, "error": null }
3.5. GET /auth/me
Восстанавливает текущего пользователя из cookie. Вызывается при загрузке приложения.
Response (200):
json
{ "data": { "user": { ... } }, "error": null }
Ошибки:
401 UNAUTHORIZED — cookie нет или токен истёк.
3.6. POST /auth/refresh (опционально)
Обновляет access-токен.
Response (200):
text
Set-Cookie: auth-token=<new-jwt>; HttpOnly; ...
Если не делаем refresh — access-токен живёт 24 часа, после чего пользователь перелогинивается.

Карточка товара.

6.3. POST /products (только seller)
Создание товара.
Body:
json
{
  "title": "Керамическая чашка",
  "description": "Ручная лепка",
  "image": "https://...",
  "price": 1800,
  "saleMode": "online",

400 VALIDATION_ERROR.

Body: Partial<Product> (без id, sellerId, seller, createdAt).

404 NOT_FOUND.

Response (200): { data: null, error: null }.

Товары текущего продавца. Отдельный эндпоинт, потому что бэк сам знает sellerId из cookie.

Часть 8. Orders
8.1. POST /orders
Создание заказов из корзины.
Body:
json
{
  "groups": [
    {
      "sellerId": "s1",
      "delivery": "cdek",
      "items": [
        { "productId": "p1", "quantity": 2 },
        { "productId": "p3", "quantity": 1 }
      ],
      "pickupPoint": null
    },
    {
      "sellerId": "s1",
      "delivery": "pickup",
      "items": [{ "productId": "p2", "quantity": 1 }],
      "pickupPoint": { "city": "Москва", "address": "ул. Ленина, 5" }
    }
  ],
  "contact": {
    "name": "Иван Петров",
    "phone": "+7 999 123-45-67",
    "email": "user@example.com"
  }
}
Что бэк делает:
Проверяет, что все товары существуют, saleMode === "online", inStock >= quantity.
Берёт цены из БД (не доверяет клиенту).
Для каждой группы создаёт отдельный Order (по продавцу + доставке).
Списывает со склада (inStock -= quantity).
Инициирует платёж через YooKassa.
Возвращает заказы + ссылку на оплату.
Response (201):
json
{
  "data": {
    "orders": [
      { "id": "ord1", "total": 5000, "status": "created", ... },
      { "id": "ord2", "total": 3200, "status": "created", ... }
    ],
    "paymentUrl": "https://yoomoney.ru/checkout/..."
  },
  "error": null
}
Ошибки:
400 VALIDATION_ERROR — товар закончился / не найден.
401 UNAUTHORIZED — не залогинен.
8.2. GET /orders
Заказы текущего пользователя.
Поведение зависит от роли:
Если buyer — его покупки.
Если seller — если query ?role=seller — входящие заказы.
Если обе роли — по умолчанию buyer.
Query: ?role=buyer|seller&status=&page=&pageSize=
Response: Paginated<Order>.
8.3. GET /orders/:id
Response: Order.
Проверка прав: юзер должен быть либо buyer этого заказа, либо seller.
Ошибки: 403 FORBIDDEN, 404 NOT_FOUND.
8.4. PATCH /orders/:id/status (только seller)
Смена статуса.
Body:
json
{ "status": "shipped", "trackingNumber": "CDEK123456789" }
Валидные переходы:
paid → shipped
shipped → delivered
любой (до shipped) → cancelled
Response: обновлённый Order.
Ошибки:
403 FORBIDDEN — не seller этого заказа.
400 VALIDATION_ERROR — недопустимый переход.
8.5. POST /webhooks/yookassa (внутренний)
YooKassa вызывает бэк при успешной оплате. Бэк меняет статус created → paid.
Фронт этот эндпоинт не вызывает. Но бэк должен его реализовать — иначе оплата не подтвердится.

Альтернатива: фронт делает три отдельных запроса (GET /orders?role=seller&status=paid, GET /seller/products, GET /orders?role=seller) и агрегирует на клиенте. Это проще для бэка, но медленнее (3 запроса).
Рекомендую: один /seller/dashboard — быстрее, меньше кода на фронте.

Часть 12. Uploads (опционально)

Для MVP — не нужно.
